# 1008CPE_file：表7标准双链路文件传输测试

接收端从发送端通过Wi-Fi和CPE两路下载，使用原1008CPE模糊PID分配文件块，合并后校验SHA256。默认按“表7 单业务流发包模型”定时发送，完成规定次数后自动结束。原1008CPE视频工程使用独立目录、仓库和端口。

## 标准规格与计数口径

| 业务 | 文件大小 | 包头到包头间隔 | 业务数量 | 周期窗口 |
| --- | ---: | ---: | ---: | ---: |
| 小文件 | 200 B | 20 ms | 133200 | 44分24秒 |
| 中文件 | 8000 B（8 kB） | 50 ms | 10800 | 9分钟 |
| 大文件 | 1500000 B（1.5 MB） | 6 s | 66 | 6分36秒 |

截图没有说明单位进制、三类排列方式以及“数据包”的层次。本工程明确采用以下实验口径，得到完整标准文档后可再核对：

- kB/MB按1000换算。
- 一份完整文件计一次业务；UDP分片、请求、保活和重传不增加业务次数。
- 单业务流默认按小→中→大分段发送，三段周期总和恰好3600秒。总业务数144066，总有效数据212040000字节。注册、开始前准备时间和最后的下载排空另计。
- 两路共同承载一个业务流。200 B和8 kB文件各只有一个32 KiB文件块，按PID选择其中一路；1.5 MB文件拆为多个块跨两路下载。

## 连接与启动

发送电脑支持Python 3.8或更新版本，接收电脑要求Python 3.10或更新版本。下载完整仓库，**两端都更新并重新启动**。

1. 发送电脑连接路由器Wi-Fi。
2. 接收电脑网线连接CPE，同时连接同一Wi-Fi，或使用手机USB共享该Wi-Fi。手机共享Wi-Fi时关闭移动数据。
3. 发送端双击`send/start.cmd`，接收端双击`receive/start.cmd`，允许Windows管理员提示。
4. 两路注册成功后自动执行表7完整测试，约一小时后退出。按Ctrl+C可以提前中止，记录会标为未完成。

云IP、端口、公开实验token均已填好，两端本机IP自动识别。发送端标准文件放在独立的`send/standard_files/`，首次启动自动生成200/8000/1500000字节的三个文件；旧`send/files/`中的个人文件保留。标准目录已有同名文件但大小不符时会报错，不覆盖。

发送端也可以手动启动：在工程根目录运行`python send/main.py`，或进入send目录运行`python main.py`。使用多个Python版本时可用`py -3.8 send/main.py`。手动启动时若Windows提示防火墙访问，请允许实际Wi-Fi网络的入站访问；双击start.cmd会自动设置实验端口规则。

## 时间控制

接收端先与发送端建立标准测试会话。发送端使用自己的单调时钟确定统一开始时刻，随后按`开始时刻 + 类型偏移 + 序号 × 间隔`发送。接收端默认提前250 ms请求任务；发送端收到请求后等待规定时刻，再发送文件数据。两条支路共享发送端时钟。

接收端允许多个业务同时在途，默认窗口32。下载完成和下一业务的发送时刻相互独立；链路或窗口无法承载负载时会报错或记录迟到，程序不会通过降低规定频率来伪装通过。每个块缺片仍在同一路有限重传，不跳缺块、不自动换路。

`files.csv`记录发送端应用层首个文件数据报的发送起始时刻、相邻业务间隔、相对计划的迟到量及SHA256。`request_to_complete_seconds`从提前请求计至校验完成，包含定时等待。这是软件测量，非网卡硬件时间戳。Windows使用高精度内核定时器，兼容Python3.8的等待精度；运行期间申请1 ms计时精度，退出时恢复。

截图未给出计时容差。工程默认用5 ms作为观察阈值`standard_timing_tolerance_ms`，**它不属于截图中的标准条款**；计划间隔始终为20 ms/50 ms/6 s。`summary.json`分别记录`counts_complete`和`timing_ok`，文件传输完成但计时超差仍会标记`timing_ok=false`。需要严格零误差判定时可把阈值设为0。

## 可选测试方式

以下命令在管理员终端执行，通常直接双击启动即可。

```powershell
# 只测某一类，仍使用表中的完整次数
python receive/main.py --profile small
python receive/main.py --profile medium
python receive/main.py --profile large

# 调试：每类仅两次，大小和间隔不变，周期窗口12.14秒
python receive/main.py --count-limit 2

# 60秒提前停止；记录会标记未完成，不算完整标准测试
python receive/main.py --duration 60

# 固定五五替代PID，用于对照
python receive/main.py --mode fixed

# 旧的不定时循环模式，两端都切换
python send/main.py --model loop
python receive/main.py --model loop --rounds 1
```

`--count-limit`默认0，使用完整标准次数。正数为每类次数上限；结果会标记`full_standard_counts=false`，不能当作一小时标准验收。旧循环模式仍使用`send/files/`中的文件，空目录生成1/3/5 MB示例文件；轮数0表示不限。标准模式不接受`--rounds`。

## 链路和PID

```text
请求方向：
  Wi-Fi：接收程序 → Wi-Fi/手机USB → 发送端文件服务
  CPE： 接收程序 → CPE → 阿里云UDP30017 → 发送端的UDP映射

文件返回：
  Wi-Fi：发送端 → Wi-Fi/手机USB → 接收程序
  CPE： 发送端 → 阿里云UDP30016 → 云端UDP30017 → CPE → 接收程序

接收端：按文件位置合并 → 大小/SHA256校验 → 记录业务完成
```

发送端向云端公告LAN地址并保活；接收端经CPE获取发送端地址，再经Wi-Fi/USB注册发送端。网卡/路由自动识别，多候选时提示选择。路由器应允许Wi-Fi客户端互通。

原PID规则表、整数输出、20单位窗口、暖机>10及`G=clip(5+4.5*u,0,10)`保留。一个调度单位为文件块，反馈是已下载、等待顺序合并的两路块数；控制器跨全部标准业务连续运行。标准模式增加并发预请求来维持业务节奏，实验条件与旧的视频模式和每路仅一个在途块的循环模式不同。

## 结果

每次接收在`receive/results/日期时间_编号/`新建目录：

- `downloads/`：各类文件最新完整副本；未完成内容保留`.part`。
- `files.csv`：业务序号、类型、实际大小、规定起始时刻、发送端首包时间/间隔/迟到、计时超差、预请求至完成耗时、SHA256和状态。
- `blocks.csv`：各块的路径、大小、重试和耗时。
- `throughput.csv`：两路接收字节/速率、待合并块数和G。
- `control.csv`：调度块数、PID周期、缓存输入、G和更新次数。
- `config.json`、`summary.json`：参数、标准计划、完整次数/缩短测试标识、完成数量及计时结果。

只保留每类文件最新副本，CSV逐业务记录全部次数。接收字节包含重复/重传正文，不含UDP/IP/HMAC头；有效字节见`files.csv`。生成的文件、个人文件、下载结果和私钥均不上传GitHub。

## 云端与验证

固定云地址47.97.248.31，LAN端口UDP30012，云端UDP30016/30017，接收端CPE本地UDP30016。独立云目录`/root/1008CPE_file`，常驻服务`1008cpe-file-relay.service`。云控制台允许UDP30016/30017；原视频30006/30007和原服务保留。新协议增加标准会话和首包时间回传，云端已同步协议；用户无需手动改服务器。

```powershell
python -m unittest test_file_download test_standard_download -v
```

覆盖旧循环、PID暖机、同路缺片重传、乱序/重复、损坏/断路拒绝，以及标准三类尺寸/次数、发送端绝对定时、慢下载下的并发发包、首包测量丢失后的重传、计时超差记录。

标准模式的自动测试使用缩短次数和回环链路，不等同于真实Wi-Fi/CPE完整一小时验收。改造前的真实双机9 MB测试已经通过，其结果验证链路连通性；表7完整次数和计时表现需要使用新版本另外实测。
